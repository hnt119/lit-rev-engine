## I3 interfaces

`PubMedClient(email, api_key=None, tool="lit-rev-engine", *, transport=None, sleep=None, monotonic=None, timeout=30, max_attempts=3)` initializes no network until `request(endpoint, params) -> bytes`. Endpoint is `esearch.fcgi` or `efetch.fcgi` at the fixed HTTPS NCBI E-utilities base URL. POST URL-encoded parameters; append tool/email and optional API key only in the transport request. Injectable `transport(url, data, timeout) -> bytes` supports offline evaluation; default uses urllib. No third-party dependency or settings/dotenv import. Validate nonempty email/tool, positive finite timeout, positive integer attempts.

Serialize requests within a client and throttle each attempted request to at most 3/s without key, 10/s with key. Retry transient 429/5xx and transport timeouts/errors only, bounded by `max_attempts`; honor Retry-After when supplied (seconds or HTTP date), otherwise exponential backoff. No retries for other HTTP errors or malformed response data. Inject clock/sleep for deterministic tests. Wrap failures in a clear `ValueError`/`PubMedError` (subclass ValueError); errors and saved receipts must never expose credentials. Rate limiting covers this client; shared-IP/process coordination remains a documented limit.

`capture_pubmed_search(query, destination, *, client=None, email=None, api_key=None, sort="pub_date", filters=None, batch_size=200) -> dict` saves one validated capture. Query is a nonempty string retained exactly. Sort accepts `pub_date` or `relevance`; filters is an object containing only optional `datetype`, `mindate`, `maxdate`, with all three supplied together, nonempty strings, and a verified PubMed date type (`pdat`, `edat`). Validate dates as YYYY, YYYY/MM, or YYYY/MM/DD, including real calendar dates and noninverted ranges; never rewrite supplied text. Other field restrictions can remain explicitly in the original query. Batch size is an integer 1..200. A default client requires configured email; an injected client implements `request(endpoint, params)` and can be used without credentials.

1. Issue one ESearch with db=pubmed, exact term/query, retmode=xml, retstart=0, retmax=10000, usehistory=y, chosen sort/date filters. Capture UTC start/search/completion times separately. Do not repeat ESearch to paginate against a changing membership.
2. Strictly parse ESearch XML: root eSearchResult, valid nonnegative Count, RetStart=0, RetMax equal to returned ID length, IdList of normalized valid unique PMIDs, QueryTranslation present, history tokens present for nonzero results. RetMax is the number actually shown, not the requested upper limit. Reject external/internal ENTITY declarations and XML error elements/ErrorList (even HTTP 200). Preserve WarningList, translation, history tokens, complete response bytes. A declared Count >10,000 fails clearly before EFetch. Count must equal captured ID length; no implicit truncation.
3. Fetch the captured PMID list in batches using explicit comma-separated IDs, db=pubmed and retmode=xml. This avoids relying on expiring history tokens for record retrieval. Validate each fetched batch and the final union: valid supported PubMed XML, one normalized PMID per record, no repeated/unexpected/missing PMIDs, exact membership equality with captured IDs. Do not rely only on counts. Returned batch order may differ; combine final records in captured search order. Use the existing importer for record validation and preserve original batch bytes separately.
4. Zero results generate a valid empty PubmedArticleSet and a complete zero-result receipt without EFetch. No clinical findings are invented.
5. Build in a temporary directory beside the destination; destination must be absent (reject an existing file/directory without modifying it). Publish the complete directory only after all validation. On failure/interruption, no complete receipt/output destination; clean staging files. Rerunning after failure executes a new search; no automatic resume in v1. Failures must never modify the SQLite ledger (the adapter has no ledger access).

## Durable capture and receipt schema

Return `{"directory": absolute_path, "xml_file": absolute_path, "receipt_file": absolute_path, "receipt": dict}`. Saved names: `search.xml` (exact ESearch bytes), `batches/0001.xml` etc. (exact fetched bytes), `records.xml` (combined validated PubmedArticleSet in captured PMID order), `receipt.json`.

`receipt.json` JSON fields are frozen:

- `schema_version`: 1; `source`: "PubMed"; `adapter`: "lit-rev-engine.pubmed.v1".
- `query`: exact submitted string; `query_translation`: returned string; `sort`: chosen value; `filters`: exact user filter object.
- `started_at`, `searched_at`, `completed_at`: UTC ISO strings. `searched_at` identifies the ESearch execution, not the later ledger import.
- `reported_count`: Count; `pmids`: complete ordered normalized strings; `fetched_count`: actual validated count; `complete`: true only after exact membership validation.
- `warnings`: ordered list of `{code, message}` from WarningList, not silently discarded; `history`: `{webenv, query_key}` (null allowed only for zero results).
- `requests`: ordered list with `endpoint`, actual noncredential `params` (no API key), `response_file` (relative saved name), `response_sha256`; include search and successful fetch responses. Tool/email are operational client configuration, not search filters; don't add credentials to metadata.
- `records_file`: "records.xml"; `records_sha256`: SHA-256 of the combined file bytes.

Serialize JSON with finite values and deterministic ordering. Timestamps describe a real capture, so different searches need not have identical receipts. API keys never appear in output dictionaries, saved parameters, or errors. Saved source data are not NCBI-signed attestations; checksums establish internal consistency.

## Next integration gate (I4, queued)

Coordinator will extend SearchRunSpec with dedicated execution provenance and freeze verification/import interfaces after E3. Add a live PubMed CLI command that captures then imports only complete verified artifacts, and an offline replay command preserving the original search receipt. Receipt and hashes must survive ledger reopen/export; old imports/idempotency must remain compatible. Explicit pending queries are not executed until the user runs a command. CLI tests use injection/saved captures without live medical searches.

Durability decision: store validated capture artifacts as SQLite BLOBs in the same transaction as the run/occurrences. A path alone is insufficient if the original capture directory is moved or deleted. Export those bytes beneath `search_captures/<search_run_id>/` with an asset manifest; generic offline imports retain the existing nine-file export shape. Execution provenance is a dedicated optional SearchRunSpec field, never hidden in user filters. Empty execution/artifact fields must preserve old keyed-import fingerprints. Freeze exact method/schema names at the I4 gate. Saved XML parsing must use the same captured bytes that are hashed and stored, avoiding independent rereads of mutable files.

R5 prerequisite: `src.review.importers.load_records_bytes(content, format, source_name="<memory>") -> list[BibliographicRecord]`. Content must be bytes; explicit format supports the existing aliases. Decode UTF-8/BOM once, retain the same validation/raw provenance/contextual ValueError behavior as path imports, and make no file/network/model calls. Existing `load_records(path, format=None)` behavior stays compatible and delegates shared parsing. Retrieval owns this small importer extension and focused parity tests; no ledger changes.

## I4a frozen verification and ledger interfaces

- `validate_pubmed_artifacts(artifacts: dict[str, bytes]) -> dict` returns `receipt` and `records` (BibliographicRecord list), with no file/network calls. Require receipt.json, search.xml, records.xml and exactly the ordered batch files named in the receipt. Validate schema/version/source/adapter, complete true, typed fields (booleans are not counts), UTC chronological timestamps, strict JSON without duplicate keys/nonfinite values, every byte hash, original/query translation/filter/sort/history/warnings agreement with search XML, noncredential request params, ordered batch partition of captured PMIDs, and every fetched record. Combined XML must match the source batch records' content in captured order, not just PMIDs/counts. Reject absent/extra artifacts, unknown relative paths, incomplete data, and receipt/source contradictions. Checksums are not provider signatures.
- `verify_pubmed_capture(directory) -> dict` returns the existing capture return shape (`directory`, `xml_file`, `receipt_file`, `receipt`) after byte validation. Read each receipt-declared allowed artifact once, reject symlinked artifact paths or paths escaping the selected directory, then validate that byte snapshot. Ignore unrelated directory files such as annotations or .DS_Store without storing or modifying them; the in-memory artifact mapping itself must have exactly the required files. No modifications or external calls.
- `import_pubmed_capture(store, project_id, directory, idempotency_key=None) -> dict` verifies a single loaded byte snapshot, constructs SearchRunSpec(source="PubMed", query=receipt.query, searched_at=receipt.searched_at, filters=receipt.filters, import_format="pubmed_xml", source_file=absolute records path, source_sha256=receipt.records_sha256, reported_count=receipt.reported_count, execution=receipt), and imports those parsed records plus exact artifact bytes. Never independently reopen XML for parsing. Return the existing import result shape.
- SearchRunSpec gains optional `execution: dict | None = None` (coordinator model edit). `ReviewStore.import_records(..., idempotency_key=None, *, artifacts=None)` gains optional filename/bytes mapping. Empty/None execution and artifacts must preserve the old spec/record fingerprint exactly. Nonempty artifacts require a validated PubMed execution receipt, and nonempty execution requires its complete matching artifact mapping; there is no receipt-only import path. Receipt, records, and search spec fields must agree. Include artifact hashes in new capture fingerprints. For validated captures only, omit source_file location from the fingerprint so relocating identical bytes/receipt or replaying an exported capture under the same key returns the original run and retains its original stored path/history. All other spec fields and all receipt/artifact content remain significant; generic imports retain exact-spec/path semantics. Both validation failures and canonical-identity conflicts roll back the entire run/records/artifacts. Changed receipt/bytes under the key fails.
- A new immutable SQLite search-artifacts table stores bytes/hash/relative name and project/run foreign keys. Create it compatibly on existing ledgers. `get_search_artifacts(project_id, search_run_id) -> dict[str, bytes]`; unknown/cross-project runs fail, generic runs return `{}`. Public history always includes execution (None for old/generic imports). Avoid adding empty execution to stored/fingerprinted legacy specs.

Direct capture imports use an absolute source_file path ending in records.xml, consistent with the capture wrapper. The path need not remain present after import; verified stored artifact bytes are the durable source. The capture-specific keyed fingerprint ignores that location.
- Export captures from the same explicit read snapshot as counts/records. Each captured run's bytes go to `search_captures/<run_id>/<relative_name>`. `project.json` includes `search_artifacts` manifest entries (`search_run_id`, `name`, `sha256`, `size_bytes`, `export_file`) when any exist. `search_runs.csv` gains an execution JSON column (blank for generic runs). Generic imports still produce nine files; capture exports add their named artifact paths to result.files. Validate stored hashes before output; preserve unrelated destination files and retain deterministic bytes.
